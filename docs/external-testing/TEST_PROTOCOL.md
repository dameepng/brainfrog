# BrainFrog Facilitator-Independent Test Protocol

This document defines the formal protocol for conducting external developer validation on **BrainFrog v0.1.0-rc1**.

---

## 1. Guiding Principle: Unassisted "Cold-Start" Evaluation

To ensure BrainFrog's public beta readiness, external validation is designed as a **facilitator-independent, black-box usability test**.

> **The Core Test**: Can an unfamiliar software developer clone the repository, understand the value proposition, and successfully verify agent work in under 5 minutes relying **strictly on the public documentation**?

- **No Coaching**: Facilitators must never provide verbal hints, explain error messages, or dictate shell commands.
- **Natural Failure Paths**: If a tester gets stuck or misunderstands a concept, that friction is valuable diagnostic data, not a tester mistake.
- **Zero-Credential Invariant**: Testers must **never** be asked for an API key or credit card to evaluate the verification runtime.

---

## 2. Participant Profile

Target participants should meet the following baseline profile:
- Comfortable with Git and command-line interfaces.
- Familiar with Python project conventions (virtual environments, pip).
- Has experience using or evaluating AI coding assistants (e.g. Copilot, Cursor, Claude Code, Aider), or maintains CI/CD quality gates.

---

## 3. Protocol Execution Stages

### Stage 1: Cold Discovery & Setup (Target: < 3 min)
1. **Prompt to Tester**: *"Please open the repository at `https://github.com/dameepng/brainfrog` and follow the instructions to get started on your local machine."*
2. **Tester Actions**:
   - Clones repository.
   - Sets up virtual environment and activates it.
   - Installs dependencies (`pip install -r requirements.txt; pip install -e .`).
   - Runs `brainfrog --help` to confirm entrypoint availability.
3. **Observation Metrics**:
   - Did the tester choose the correct shell activation command?
   - Did any dependency conflict or install error occur?
   - Recorded duration: `t_setup`.

### Stage 2: Quickstart Execution (Target: < 2 min)
1. **Prompt to Tester**: *"Follow the quickstart to run the offline verification walkthrough."*
2. **Tester Actions**:
   - Runs `python demo/reproducible_proof_demo.py`.
   - Observes execution of Scenario 1 (VERIFIED), Scenario 2 (FAILED + rollback), and Scenario 3 (INVALID tamper detection).
3. **Observation Metrics**:
   - Did the demo complete without network/API prompts?
   - Did the tester understand that Scenario 2 and Scenario 3 demonstrated intentional failure modes?
   - Recorded duration: `t_demo`.

### Stage 3: Proof Evidence Exploration (Target: < 5 min)
1. **Prompt to Tester**: *"Explore the proofs generated by the demo using the BrainFrog CLI."*
2. **Tester Actions**:
   - Discovers available proofs (`brainfrog proofs` or `brainfrog list-proofs`).
   - Inspects detailed execution history (`brainfrog show-proof latest` or specific task ID).
   - Runs deterministic verification gate (`brainfrog verify-proof latest --check-workspace`).
3. **Observation Metrics**:
   - Did the tester find the Rich tables and evidence breakdown intuitive?
   - Did the tester notice the captured stdout/stderr, git commit SHAs, and SHA-256 hashes?

### Stage 4: Edge Case Probe (Optional / Exploratory)
1. **Prompt to Tester**: *"Try running verify-proof on a nonexistent task, or modify a file to see how BrainFrog responds."*
2. **Tester Actions**:
   - Evaluates `brainfrog verify-proof nonexistent` -> observes `INCOMPLETE` / `MISSING` (exit code 2).
   - Evaluates `--check-workspace` against modified files -> observes `INVALID` (exit code 1).
3. **Observation Metrics**:
   - Did exit codes and diagnostic messages clearly convey the exact reason for rejection?

### Stage 5: Debrief & Feedback Collection
1. **Prompt to Tester**: *"Please complete the feedback form in `docs/external-testing/FEEDBACK_TEMPLATE.md`."*
2. **Collection**: Gather completed form, review recorded timestamps, and archive tester logs.

---

## 4. Observer Guidelines (For Moderated Sessions)

If conducting an observed live session (e.g. over screen-share):

| Situation | Observer Action |
| :--- | :--- |
| **Tester asks: "Which command should I run?"** | *"Please follow what the README suggests."* |
| **Tester asks: "Is it supposed to fail on Scenario 2?"** | *"What does the output in your terminal indicate?"* |
| **Tester encounters terminal crash or syntax error** | Do not intervene unless requested. Note exact traceback. |
| **Tester is silent for > 60 seconds** | Ask: *"What are you looking at right now?"* or *"What do you expect to happen here?"* |

---

## 5. Success Criteria & Release Gate Metrics

The external validation sprint is evaluated against quantitative readiness thresholds:

| Metric | Target | Pass / Fail Rule |
| :--- | :---: | :--- |
| **Cold-Start Completion** | **>= 85%** | Percentage of testers who complete Stage 1 & Stage 2 without facilitator intervention. |
| **Time to First Value** | **< 5 min** | Median duration from `git clone` to completion of `reproducible_proof_demo.py`. |
| **Conceptual Clarity** | **>= 80%** | Percentage of testers who correctly articulate that `FAILED` produces a valid proof of failure rather than an `INVALID` artifact. |
| **Critical Defects** | **0** | Zero P0 (safety/data-loss) or P1 (install/correctness blocker) issues reported. |
